Melodix：一个用 Tauri + React 写的跨平台音乐播放器

Ianz2026-10-142026-10-14

为什么又做一个播放器

市面上的音乐播放器不少，但我自己用的时候总差几件事：

  • 想要逐字歌词（就是 KTV 那种字跟着唱走），大多数桌面端只有整行高亮
  • 想下载到本地，但下载完的歌在别的播放器里常常没封面、没歌词
  • 想在一个应用里同时搜 QQ 音乐和网易云（两个平台的曲库并不重合）

索性自己写一个。这就是 Melodix。

它做什么

  • 在线音乐搜索与播放 —— QQ 音乐、网易云音乐多源
  • QRC 逐字歌词 —— QQ 音乐的字符级时间轴，还支持翻译
  • 下载管理 —— 任务队列、断点续传、优先级控制、自动重试
  • 本地音乐库 —— 自动导入、元数据解析、封面与歌词自动补齐
  • 收藏与歌单管理
  • 玻璃拟态 UI，支持主题切换
  • 离线可用 —— 封面歌词本地持久化，断网不丢

技术栈

层 用什么
前端 React 19、TypeScript、Zustand、Framer Motion、Vite
后端 Tauri 2（Rust）、rusqlite、lofty、reqwest
Sidecar Node.js（meting-api）

语言构成大致是 TypeScript 56%、JavaScript 35%、Rust 4%。

几个设计上的取舍

为什么选 Tauri 而不是 Electron

最直接的原因是体积。Electron 应用动辄 100 MB+，Tauri 用系统自带的 WebView，
打包出来通常只有它的十分之一。对一个”听个歌”的工具，这个差别很实在。

代价是 Rust 侧要自己写。这个项目里 Rust 主要负责：

  • 用 rusqlite 做本地数据库（歌单、下载任务、元数据）
  • 用 lofty 解析音频标签（这首歌是什么专辑、谁唱的、第几首）
  • 用 reqwest 跑下载和网络请求

为什么歌词要专门做 QRC

QQ 音乐的歌词不是 LRC，而是它自家的 QRC 格式 —— 里面是每个字的时间戳，
不是每一行。解析出来才能做逐字高亮。

这块是纯前端解析的：把 QRC 的时间轴按字符切开，播放时按当前时间算该亮哪个字。
没有依赖额外的原生库。

为什么有 Node.js sidecar

音乐源接口（meting-api）是现成的 Node 生态，用 Tauri 的 sidecar 机制带一个
精简的 Node 运行时。换来的是不用自己逆接口。

一些实现上的细节

下载队列不是简单的”点一个下一个”，而是带优先级和断点续传的：
任务落库，中断后能从已下载的字节数继续，失败自动重试。
这样关掉应用再打开，没下完的还在。

元数据补齐：下载完的歌会自动读 ID3 标签，封面和歌词如果源里有就一并存到本地。
所以之后断网，这些也都在。

状态管理用 Zustand 而不是 Redux —— 这个应用的状态虽然多（播放器、队列、
下载、UI），但没有很深的嵌套，Zustand 的 store 切片更直接。

现状

  • 仓库：https://github.com/Ianzhyh/melodix
  • 安装包在 GitHub Releases，
    Windows 下 .msi / .exe 双击即用
  • 环境要求：Node.js 18+、Rust（stable）、Windows SDK / Xcode
  • License：见仓库

接下来想做的

  • 歌词编辑器（QRC 时间轴手改）
  • 音效均衡器
  • 更多音乐源
  • macOS / Linux 打包验证

如果你也在用 Tauri 写桌面应用，欢迎来交流踩坑经验 —— 尤其是 Windows 下
WebView2 与 sidecar 的打包细节，文档比实际遇到的坑少得多。
